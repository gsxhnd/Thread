## 1. 分层架构

Thread 采用 **前端表现层 + Tauri 桥接层 + Rust 领域层 + 数据层** 的分层结构。前端不直接触碰数据库文件与 AI Key，所有敏感操作经 Rust 后端。

```mermaid
flowchart TD
    subgraph FE [前端表现层 React]
        View[视图/组件 shadcn-ui]
        Editor[TipTap 编辑器]
        Store[Zustand Store]
        Api[IPC 封装 src/lib/api]
    end

    subgraph Bridge [Tauri 桥接层]
        Invoke["invoke 请求"]
        Emit["emit 事件"]
    end

    subgraph BE [Rust 领域层]
        Cmd[Command Handlers]
        Svc[Domain Services]
        AiSvc[AI Service]
        Repo[Repository]
    end

    subgraph Data [数据层]
        DB[(SQLite)]
        FS[文件系统 assets]
        KC[(钥匙串 API Key)]
    end

    Cloud[(云同步 Phase5 预留)]

    View --> Store
    Editor --> Store
    Store --> Api
    Api --> Invoke --> Cmd
    Cmd --> Svc
    Svc --> Repo --> DB
    Svc --> FS
    AiSvc --> KC
    Cmd --> AiSvc
    Emit -.状态推送.-> Store
    Svc -.预留.-> Cloud
    AiSvc -.->|OpenAI 兼容 API| External[外部/本地模型]
```

## 2. 职责边界

| 层 | 职责 | 不负责 |
| --- | --- | --- |
| 前端表现层 | 渲染、交互、编辑器状态、本地 UI 状态、乐观更新 | 数据持久化、AI Key、SQL |
| Tauri 桥接层 | `invoke` 调用、`emit` 事件、类型序列化 | 业务逻辑 |
| Rust 领域层 | 业务规则、事务、AI 转发、校验 | UI 逻辑 |
| 数据层 | SQLite 持久化、资源文件、Key 安全存储 | 业务规则 |

**核心原则**：

- 前端通过 `src/lib/api` 的 typed wrapper 调用后端，禁止在组件里散落 `invoke`。
- Rust 侧 command 只做参数校验与编排，具体逻辑落在 service，数据访问落在 repository。
- AI Key、数据库写入等敏感操作只在 Rust 侧发生。

## 3. 关键数据流

### 3.1 写作保存流（autosave）

编辑器变更后进入防抖，序列化为 Markdown，经 IPC 落库，成功后回推保存状态。

```mermaid
sequenceDiagram
    participant U as 用户
    participant E as TipTap 编辑器
    participant S as Zustand Store
    participant A as IPC 封装
    participant C as chapter_save 命令
    participant R as Repository
    participant DB as SQLite

    U->>E: 输入正文
    E->>S: onUpdate 更新草稿状态
    Note over S: 防抖 800ms 合并变更
    S->>A: saveChapter(id, markdown)
    A->>C: invoke chapter_save
    C->>C: 校验 + 计算字数
    C->>R: upsert 正文 + updated_at
    R->>DB: UPDATE chapters
    DB-->>R: ok
    R-->>C: ok
    C-->>A: {savedAt, wordCount}
    A-->>S: 更新「已保存」状态
    S-->>E: 显示保存指示器
```

**要点**：

- 防抖窗口默认 800ms；窗口失焦（`blur`）或切换章节时强制立即保存。
- 保存失败进入重试队列并在 UI 提示，避免丢字。
- 后端每次保存记录 `writing_sessions`（字数增量、时长）供统计模块使用。

### 3.2 伏笔关联流（setup → payoff）

伏笔是差异化核心：埋设点与呼应点均指向具体章节，可视化未回收提醒。

```mermaid
sequenceDiagram
    participant U as 用户
    participant V as 伏笔面板
    participant A as IPC 封装
    participant C as foreshadowing_link 命令
    participant Svc as Foreshadow Service
    participant DB as SQLite

    U->>V: 选择伏笔并指定 setup/payoff 章节
    V->>A: linkForeshadowing(fid, setupChapterId, payoffChapterId)
    A->>C: invoke foreshadowing_link
    C->>Svc: 校验章节存在 + 状态流转
    Svc->>DB: UPDATE foreshadowings 设置关联与状态
    DB-->>Svc: ok
    Svc-->>C: {status: planted/resolved}
    C-->>A: 结果
    A-->>V: 刷新伏笔列表与「未回收」计数
```

**状态流转**：`planted`（已埋设，仅有 setup）→ `resolved`（已回收，setup 与 payoff 均存在）。未回收伏笔在导航侧栏与统计中高亮提醒。

### 3.3 AI 请求流（BYOK，支持流式）

前端发起 AI 请求，Rust 从钥匙串取 Key，转发至 OpenAI 兼容端点，流式结果经 `emit` 增量回推。

```mermaid
sequenceDiagram
    participant U as 用户
    participant P as AI 面板
    participant A as IPC 封装
    participant C as ai_complete 命令
    participant AiSvc as AI Service
    participant KC as 钥匙串
    participant LLM as OpenAI 兼容端点

    U->>P: 选中文本/输入指令 (续写/润色)
    P->>A: aiComplete(prompt, context)
    A->>C: invoke ai_complete
    C->>KC: 读取 apiKey / baseURL / model
    C->>AiSvc: 组装请求 (含设定上下文)
    AiSvc->>LLM: POST /v1/chat/completions (stream)
    loop 流式分片
        LLM-->>AiSvc: token chunk
        AiSvc-->>P: emit ai://chunk
    end
    LLM-->>AiSvc: [DONE]
    AiSvc-->>C: 完成
    C-->>A: {finishReason}
    A-->>P: 结束流式，允许采纳/丢弃
```

**要点**：

- Key 只在 Rust 侧读取与使用，绝不返回前端。
- 支持流式（`emit` 增量）与非流式两种模式，超时与重试在 AI Service 统一处理。
- 上下文注入：可携带当前章节、相关人物/世界观设定，便于「基于设定的问答」。

## 4. 错误处理

- **Rust 侧**：统一 `AppError`（`thiserror`），序列化为 `{ code, message }` 返回前端。
- **前端侧**：`src/lib/api` 捕获并归一化，通过 toast 呈现；可重试错误（保存/AI）进入重试逻辑。
- **错误码约定**：见 [04.ipc-api.md](04.ipc-api.md)。

---

## 5. autosave 与并发约定

- 单窗口单项目，写操作以「最后写入生效」为主；同一章节的保存请求按序列化排队，避免竞态。
- 长耗时任务（AI、导出）异步执行并通过事件反馈进度，不阻塞 UI。
- 为将来云同步预留：所有实体 `updated_at`（毫秒时间戳）+ 软删除（`deleted_at`）。
