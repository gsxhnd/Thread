# Thread / 灰线 — 架构设计

> 本文承接 [00.overview.md](00.overview.md) 第 3 节与 [01.tech-stack.md](01.tech-stack.md)，细化分层架构、职责边界与关键数据流。

---

## 1. 分层架构

Thread 采用 **前端表现层 + Tauri 桥接层 + Rust 服务层 + 数据层** 的分层结构。前端不直接执行网络请求和代理操作，所有网络 I/O 均经 Rust 后端处理。

```mermaid
flowchart TD
    subgraph FE [前端表现层 React]
        Views[视图/组件 shadcn-ui]
        ReqEditor[请求编辑器 Monaco Editor]
        ProxyViewer[代理流量查看器]
        Store[Zustand Store]
        Api[IPC 封装 src/lib/api]
    end

    subgraph Bridge [Tauri 桥接层]
        Invoke["invoke 请求"]
        Emit["emit 事件"]
    end

    subgraph BE [Rust 服务层]
        Cmd[Command Handlers]
        HttpSvc[HTTP Client Service]
        GrpcSvc[gRPC Client Service]
        WsSvc[WebSocket Service]
        GqlSvc[GraphQL Service]
        MqttSvc[MQTT Service]
        ProxySvc[Proxy Engine Service]
        CertSvc[Certificate Service]
        ScriptSvc[Script Runner 预留]
    end

    subgraph Data [数据层]
        DB[(SQLite)]
        FS[文件系统 Certs / Proto / Config]
    end

    Network((外部网络))

    Views --> Store
    ReqEditor --> Store
    ProxyViewer --> Store
    Store --> Api
    Api --> Invoke --> Cmd
    Cmd --> HttpSvc --> Network
    Cmd --> GrpcSvc --> Network
    Cmd --> WsSvc --> Network
    Cmd --> GqlSvc --> Network
    Cmd --> MqttSvc --> Network
    Cmd --> ProxySvc --> Network
    Cmd --> CertSvc --> FS
    Cmd --> ScriptSvc
    Cmd --> DB
    Emit -.流量/消息推送.-> Store
    ProxySvc -.emit 流量.-> Emit
    WsSvc -.emit 消息.-> Emit
    MqttSvc -.emit 消息.-> Emit
```

## 2. 职责边界

| 层 | 职责 | 不负责 |
| --- | --- | --- |
| 前端表现层 | 渲染 UI、请求编辑器、代理流量展示、本地 UI 状态 | 网络 I/O、TLS 处理、证书操作 |
| Tauri 桥接层 | `invoke` 调用、`emit` 事件推送、类型序列化 | 业务逻辑 |
| Rust 服务层 | 请求执行、代理引擎、协议处理、证书管理、脚本运行 | UI 逻辑 |
| 数据层 | SQLite 持久化、文件（证书/Proto/配置） | 业务规则 |

**核心原则**：

- 前端通过 `src/lib/api` 的 typed wrapper 调用后端，禁止在组件里散落 `invoke`。
- Rust 侧 command 只做参数校验与编排，具体网络操作落在各协议 service。
- 所有网络请求均在 Rust 侧发起，保证 TLS 证书操作、代理拦截等能力可控。
- 长连接（WebSocket / MQTT / gRPC streaming）通过 Tauri emit 事件向前端推送数据。

## 3. 关键数据流

### 3.1 HTTP 请求流

用户在请求编辑器中配置请求参数，发送后 Rust 执行请求并返回完整响应。

```mermaid
sequenceDiagram
    participant U as 用户
    participant E as 请求编辑器
    participant S as Zustand Store
    participant A as IPC 封装
    participant C as http_send 命令
    participant H as HTTP Client Service
    participant N as 目标服务器

    U->>E: 填写 URL / Headers / Body
    E->>S: 更新请求配置
    U->>E: 点击 Send
    S->>A: httpSend(request)
    A->>C: invoke http_send
    C->>C: 环境变量替换 / 前置脚本(预留)
    C->>H: 构建 reqwest 请求
    H->>N: HTTP Request
    N-->>H: HTTP Response
    H-->>C: 解析响应 (status / headers / body / timing)
    C->>C: 后置脚本(预留) / 保存历史
    C-->>A: HttpResponse
    A-->>S: 更新响应面板
    S-->>E: 展示响应
```

**要点**：

- 环境变量在发送前由 Rust 侧替换（`{{variable}}` → 实际值）。
- Timing 信息包含 DNS / TCP / TLS / TTFB / Total 各阶段耗时。
- 每次请求自动记录到 History，可配置是否保存 Body。
- 支持取消正在进行的请求。

### 3.2 WebSocket 会话流

WebSocket 为长连接，连接建立后通过 emit 事件实时推送收发消息。

```mermaid
sequenceDiagram
    participant U as 用户
    participant P as WS 面板
    participant A as IPC 封装
    participant C as ws_connect 命令
    participant W as WebSocket Service
    participant N as WS 服务器

    U->>P: 输入 URL，点击 Connect
    P->>A: wsConnect(url, headers)
    A->>C: invoke ws_connect
    C->>W: 建立 WebSocket 连接
    W->>N: Upgrade Handshake
    N-->>W: 101 Switching Protocols
    W-->>C: connectionId
    C-->>A: { connectionId, status }
    A-->>P: 连接成功

    U->>P: 输入消息，点击 Send
    P->>A: wsSend(connectionId, message)
    A->>C: invoke ws_send
    C->>W: 发送消息
    W->>N: Message Frame

    loop 持续接收
        N-->>W: Message Frame
        W-->>P: emit ws://message { connectionId, data, timestamp }
    end

    U->>P: 点击 Disconnect
    P->>A: wsDisconnect(connectionId)
    A->>C: invoke ws_disconnect
    C->>W: 关闭连接
```

### 3.3 代理抓包流

代理引擎在后台启动，拦截系统/浏览器流量，通过 emit 实时推送到前端。

```mermaid
sequenceDiagram
    participant App as 被抓包应用
    participant P as Proxy Engine
    participant R as 规则引擎
    participant C as Certificate Service
    participant N as 目标服务器
    participant FE as 前端流量面板

    Note over P: 用户启动代理 (端口 9090)

    App->>P: HTTP CONNECT example.com:443
    P->>C: 为 example.com 签发域名证书
    C-->>P: 域名证书 + 私钥
    P->>App: 200 Connection Established
    P->>App: TLS Handshake (域名证书)
    App->>P: 加密请求 (已解密)
    P->>R: 匹配规则 (Breakpoint / Block / Rewrite)
    
    alt 命中断点规则
        P-->>FE: emit proxy://breakpoint { 请求详情 }
        FE-->>P: 用户修改后放行
    end

    P->>N: 转发请求 (重新 TLS)
    N-->>P: 响应
    P-->>App: 转发响应
    P-->>FE: emit proxy://entry { request, response, timing }
```

**要点**：

- 代理引擎独立于主线程运行，通过 channel 与 command 层通信。
- CA 根证书在首次启动时生成，需引导用户安装并信任。
- 默认仅抓包查看，断点/修改为高级功能（Phase 4）。
- 流量数据可选保存到 SQLite 或仅内存保留，避免大量数据撑爆磁盘。

### 3.4 gRPC 调用流

```mermaid
sequenceDiagram
    participant U as 用户
    participant P as gRPC 面板
    participant A as IPC 封装
    participant C as grpc_invoke 命令
    participant G as gRPC Service
    participant N as gRPC 服务器

    U->>P: 加载 .proto 或使用反射
    P->>A: grpcLoadProto(path) / grpcReflect(host)
    A->>C: invoke
    C->>G: 解析服务/方法列表
    G-->>P: ServiceList + MethodList

    U->>P: 选择方法，填写请求 JSON
    P->>A: grpcInvoke(host, service, method, payload, metadata)
    A->>C: invoke grpc_invoke
    C->>G: 构建 gRPC 请求
    G->>N: gRPC Call
    
    alt Unary
        N-->>G: Response
        G-->>C: GrpcResponse
        C-->>A: 返回
    else Server Streaming
        loop 流式响应
            N-->>G: Response Chunk
            G-->>P: emit grpc://stream { data }
        end
        G-->>C: Stream Done
    end
```

## 4. 代理引擎架构

代理引擎是 Thread 的核心组件之一，需要独立设计。

```mermaid
flowchart TD
    subgraph ProxyEngine [Proxy Engine]
        Listener[TCP Listener :9090]
        ConnHandler[Connection Handler]
        HttpHandler[HTTP 明文处理]
        TunnelHandler[CONNECT 隧道处理]
        TlsTerminator[TLS MITM 终结]
        RuleEngine[规则引擎]
        CertCache[证书缓存]
    end

    Listener --> ConnHandler
    ConnHandler -->|HTTP| HttpHandler
    ConnHandler -->|CONNECT| TunnelHandler
    TunnelHandler --> TlsTerminator
    TlsTerminator --> CertCache
    HttpHandler --> RuleEngine
    TlsTerminator --> RuleEngine

    RuleEngine -->|Pass| Forward[转发到目标]
    RuleEngine -->|Block| Drop[丢弃/返回错误]
    RuleEngine -->|Breakpoint| Pause[暂停等待用户]
    RuleEngine -->|Rewrite| Modify[修改请求/响应]
```

**关键设计**：

- **证书缓存**：为每个域名动态生成的证书缓存在内存中（LRU），避免重复生成。
- **规则引擎**：支持域名匹配（通配符、正则）、路径匹配、方法匹配，规则按优先级排序。
- **并发模型**：每个连接一个 tokio task，使用 channel 向前端推送事件。
- **性能**：大流量下前端采用虚拟列表渲染，后端限制推送频率（批量发送 + 节流）。

## 5. 错误处理

- **Rust 侧**：统一 `AppError`（`thiserror`），序列化为 `{ code, message }` 返回前端。
- **前端侧**：`src/lib/api` 捕获并归一化，通过 toast 呈现；网络错误（超时/连接拒绝等）在响应面板内展示。
- **错误码约定**：见 [04.ipc-api.md](04.ipc-api.md)。

---

## 6. 并发与资源管理

- 多个请求可并发发送，每个请求在独立 tokio task 中执行。
- WebSocket / MQTT 长连接通过连接 ID 管理，支持多个同时活跃的连接。
- 代理引擎在后台持续运行，通过 `proxy_start` / `proxy_stop` 控制生命周期。
- 大型响应体（> 10MB）不全量加载到内存，采用分段读取。
- 为将来扩展预留：所有实体带 `updated_at`，UUID 主键。
