### 1.2 保留的通用基础设施

- `atomic_file.rs`：同目录临时文件 + rename 的原子写（阶段 0 起被所有工作区写入复用）。
- `sync_mutex.rs`：poison 恢复锁；`config.rs`：`config.toml` 分区配置骨架（新增 `session` 分区存放最近工作区）。
- `error.rs`：统一错误类型，按 [IPC 设计](04.ipc-api.md) §7 输出 `{ code, message }`（本次补齐 `NETWORK_ERROR` / `TIMEOUT` / `TLS_ERROR` / `CANCELLED` / `PROTO_ERROR` / `PROXY_ERROR`）。
- 前端壳层：`WindowTitleBar`（macOS Overlay 拖拽区）、`AppErrorBoundary`、`AppFatalScreen`、`components/ui/*`（shadcn 组件）、`i18n`、`lib/platform.ts`、`lib/tauri-listener.ts`。

### 1.3 旧数据处置路径（不删除用户数据）

旧版本的写作数据位于同一个 SQLite 文件（`<数据目录>/thread/thread.db`）。处置原则与实现：

1. **不删除、不改名、不迁移**旧表：新迁移只做 `CREATE TABLE IF NOT EXISTS`，不触碰 `projects` / `chapters` / `characters` 等表。
2. **schema 版本隔离**：旧版本只用 `_migrations` 表且从不写 `PRAGMA user_version`，因此旧库的 `user_version = 0`，会正常执行新迁移 1（只新增本地数据表）。新版本改用 `user_version` + `schema_migrations` 记录版本。
3. **可发现**：`legacy_status` 检测旧表是否存在并统计作品/章节/人物/字数，前端在欢迎页与设置页提示。
4. **可导出**：`legacy_export` 把旧表**只读**导出为
   - `tables/<表名>.json`：按 `PRAGMA table_info` 动态取列，兼容字段增删；
   - `manuscript.md`：按作品汇总章节正文；
   - `README.md`：导出统计与「原库未被修改」的说明。
   导出目录默认命名为 `thread-legacy-export-<时间戳>`。
5. **用户自行决定去留**：文档明确写出「确认导出可读后，如需清理旧表，请先备份 `thread.db`」；应用不提供自动删除。
6. **删除即回收站**：删除集合/请求/环境不是 `unlink`，而是移到 `<数据目录>/thread/trash/<时间戳>/<原相对路径>`，操作后 toast 提示回收站路径。

相关实现：`src-tauri/src/commands/legacy.rs`、`src-tauri/src/db/migrations.rs`（含「旧库被识别且旧行未被改动」的单元测试）、`src-tauri/src/workspace/files.rs::move_to_trash`。

## 2. 工作区目录与文件约定（阶段 0）

### 2.1 目录结构

```text
my-workspace/
├── thread.workspace.json          # 工作区配置（version/id/name/activeEnvironment/proxy/settings）
├── .gitignore                     # 新建工作区时生成：排除本地产物与本地覆盖文件
├── environments/
│   ├── global.env.json            # 全局变量（默认激活）
│   └── dev.env.json
└── my-api/                        # Collection 文件夹（可嵌套）
    ├── collection.json            # 集合元信息（auth/headers/scripts 被子请求继承）
    ├── users/
    │   ├── list-users.http.json
    │   └── create-user.http.json
    ├── hello.grpc.json            # 阶段 2 起的协议文件（阶段 1 只读展示）
    └── realtime/chat.ws.json
```

扫描规则：以「包含 `collection.json`，或包含请求文件，或包含子集合」的目录为集合；跳过所有以 `.` 开头的目录与 `node_modules`/`target`/`dist`/`build`/`coverage`；工作区根目录下的散落请求文件会被忽略并在 `warnings` 中提示。

### 2.2 稳定 ID

- 每个文件带可选 `id`（UUID v4），由应用创建时写入。
- **缺失 `id` 的文件（例如手写或从旧文档拷贝）不会在扫描时被改写**：其稳定标识为 `path:<工作区相对路径>`，避免打开工作区就制造 Git 改动。
- 应用保存该请求/集合时才补写真实 UUID；此后即使重命名文件或移动目录，ID 保持不变。

### 2.3 文件名与冲突

- 显示名 → 文件名：保留中英文与数字，空格、`<>:"/\|?*` 与控制字符折叠为 `-`，折叠连续分隔符，截断到 60 字符，去掉首尾 `-`/`.`（`workspace/layout.rs::slugify`）。
- 冲突处理：`name.http.json` → `name-2.http.json` → `name-3.http.json`（`unique_path`）。
- 扩展名约定：`.http.json` / `.grpc.json` / `.ws.json` / `.graphql.json` / `.mqtt.json` / `.env.json`。
- 路径安全：所有来自前端的路径经 `normalize_relative` + `resolve_inside` 校验，拒绝绝对路径与 `..`（单测覆盖 `../../etc/passwd`）。

### 2.4 写入方式

- 所有工作区文件统一走 `atomic_file::atomic_write`（同目录临时文件 + `fsync` + rename），崩溃或断电不会留下半个 JSON。
- JSON 一律 2 空格缩进 + 末尾换行：便于 diff/review。
- 版本号：每个文件带 `version`（当前为 1）；读取时兼容缺省字段，写入时补齐 `version` 与 `id`，为后续版本迁移留出空间。

### 2.5 可入库配置 vs 不入库数据

| 数据 | 位置 | 是否进 Git |
| --- | --- | --- |
| 集合、请求、环境变量（非机密）、工作区配置 | 工作区文件 | 是 |
| 机密变量（`secret: true`）的值 | `<数据目录>/thread/secrets/<workspace-key>.json` | 否（工作区文件里只有 `"value": ""` 占位） |
| 请求历史、响应快照 | `<数据目录>/thread/thread.db` | 否 |
| 大响应体 | `<数据目录>/thread/bodies/<uuid>.bin` | 否 |
| 被删除的集合/请求/环境 | `<数据目录>/thread/trash/<时间戳>/...` | 否 |

机密变量方案说明（对应路线图「跨阶段约束」）：

- 机密值**不写入可提交文件**，因此不会因为 UI 标记 `secret` 就被误当作安全；
- 该方案是「本地忽略文件」而非系统凭据库加密：阶段 5 评估脚本运行时一并决定是否接入 macOS Keychain / Windows Credential Manager；
- IPC 不返回机密值，环境页面默认显示掩码；用户点击眼睛按钮触发 `env_variable_reveal` 才会读取；
- 新建工作区生成 `.gitignore` 模板（`.thread/`、`*.local.env.json`、`*.local.*`、`.DS_Store`）。

## 3. 请求 / 集合 / 环境 / 工作区文件格式

字段与 [数据存储设计](03.database.md) §2 一致，并补充了稳定 ID（§2.2）。示例（`*.http.json`）：

```json
{
  "version": 1,
  "id": "6f1c…",
  "protocol": "http",
  "name": "Create User",
  "method": "POST",
  "url": "{{baseUrl}}/api/users",
  "queryParams": [{ "key": "page", "value": "1", "enabled": false }],
  "headers": [{ "key": "Authorization", "value": "Bearer {{apiKey}}", "enabled": true }],
  "body": { "type": "json", "content": "{ \"name\": \"John\" }" },
  "auth": { "type": "inherit" },
  "settings": { "timeoutMs": 10000, "followRedirects": true, "verifySsl": true }
}
```

- `protocol` 为 serde 内部标签：`http` / `grpc` / `websocket` / `graphql` / `mqtt`，五种协议文档都能正确读写与 round-trip（单测覆盖）。
- Body 类型：`none` / `json` / `raw`（可指定 Content-Type）/ `formUrlencoded` / `multipart`（文本字段 + 文件字段）/ `binary`（文件绝对路径）。
- 认证：`inherit`（继承集合）/ `none` / `bearer` / `basic` / `apiKey`（header 或 query）。
- 集合级 `auth`/`headers` 被最近的祖先集合继承，请求级配置优先（`AuthSpec::resolve` + `nearest_collection`，单测覆盖「嵌套集合覆盖父集合」）。

## 4. 存储验证与索引决策（阶段 0 核心问题）

### 4.1 实测数据（`workspace::index::scan_and_search_performance_is_acceptable`）

测试生成 **40 个集合 / 1200 个请求文件 / 3 个环境文件**，在本机（Apple Silicon，debug 构建）实测：

| 操作 | 结果 |
| --- | --- |
| 全量扫描 + 解析 1200 个请求文件 | **53.19 ms**（约 0.04 ms/文件） |
| 内存索引搜索 1000 次（`service-7`） | **168.31 ms**（约 0.17 ms/次） |
| 外部变更检测（路径 + mtime + 大小的指纹轮询） | 2 s 间隔，1200 文件指纹计算 < 10 ms |

复现：`cd src-tauri && cargo test --lib scan_and_search_performance -- --nocapture`

### 4.2 决策：阶段 1 **不引入 SQLite 文件索引**

理由：

- 扫描成本远低于人类感知阈值（53 ms / 1200 文件），线性外推到 5 万文件仍约 2 s，且真实工作区远小于此；
- Git 切换分支/外部编辑后的「刷新请求列表」只需一次全量重扫，无需增量索引的复杂度与一致性风险；
- 少一份可失同步的派生状态，符合「文件是真相」的原则。

复核条件（满足任一即重新评估引入 SQLite 索引）：工作区请求文件 > 5 万个、单次全量扫描 > 1 s、或需要跨工作区全文检索。

### 4.3 SQLite 只保存不可重建的本地数据

`migrations/0001_init.sql` 仅创建 `history_entries`（请求历史与响应快照）。代理流量、Cookie、证书等表按路线图在其阶段追加（只增不改）。历史清理：

- `history_limit`（应用设置，默认 1000 条）在每次写入后执行 trim；
- `history_clear` 支持按时间清理；删除条目时同步删除其大响应体文件。

### 4.4 外部编辑 / `git pull` / 切分支后的刷新链路

```text
每 2s 计算工作区指纹（路径 + mtime + size，跳过 .git 等目录）
  → 指纹变化 ⇒ 全量重扫
  → 索引摘要（digest）变化 ⇒ emit `workspace://changed`
  → 前端重新拉取索引（请求列表即时更新，标签页内的请求内容通过 react-query 失效重取）
手动刷新：侧边栏「重新扫描」按钮 → `workspace_refresh`
```

自写文件同样会触发事件，因此前端始终与磁盘一致；由于只在 digest 变化时 emit，避免了无意义的抖动。

## 6. 阶段 1（HTTP MVP）实现说明

### 6.1 能力矩阵

| 方法 / URL / Query / Headers | ✅ | `services/http.rs` |

| 认证：inherit / none / bearer / basic / apiKey(header,query) | ✅ | `services/http.rs::apply_auth` |

| 取消 | ✅ | 前端生成 `taskId`，`HttpTaskRegistry` + `oneshot` + `tokio::select!`，覆盖响应体下载阶段 |

### 6.2 计时口径（诚实标注）

- `dnsMs`：发送前对目标主机做一次 `lookup_host` 探测（IP 直连记 0）。
- `tcpMs`：探测阶段建立一次 TCP 连接并立即关闭。
- `ttfbMs`：从真正发起请求到收到响应头（包含真实 DNS/TCP/TLS 与服务器处理时间）。
- `downloadMs`：响应头到响应体读毕；`totalMs`：整个过程。
- `tlsMs`：**阶段 1 固定为 0**——不单独测量 TLS 握手，其耗时包含在 `ttfbMs` 内；精确的分阶段计时随阶段 3 的代理引擎（可在 MITM 侧获得握手阶段）一起接入。UI 已在时序面板中注明。
- 探测是「额外一次连接」，失败不影响请求结果（3 秒上限，失败记 0）。

### 6.3 安全与隐私

- 大响应体（超过 `maxInlineBodyBytes`，默认 1 MiB）流式写入本地数据目录，IPC 只返回文件路径，避免大对象穿过 IPC；下载硬上限 200 MiB。
- 机密变量值不经过 IPC（除显式 `env_variable_reveal`）。
- 请求快照写入历史时保存的是**发送时配置**与解析后的 method/url/headers，响应快照不含大 Body。

| 超时 / 取消 | `timeout_is_reported_as_a_timeout_error`、`cancel_interrupts_an_in_flight_request`（断言 150 ms 内返回 `CANCELLED`） |
| 重启后集合与环境不丢失 | 集合/环境即工作区文件，启动自动重开 + 全量扫描还原索引 |
| Git 只显示预期的配置文件变更 | 机密值本地化、历史/响应体/回收站均在工作区之外；只读扫描不写文件（无 `id` 的文件不会被补写） |

## 8. 已知限制与后续项

1. **TLS 分阶段计时**：`tlsMs` 恒为 0，将在阶段 3 代理引擎中补齐。
2. **集合/请求排序**：当前按名称排序，拖拽排序（`sortOrder`）留待后续；不影响 Git 友好性。
3. **i18n**：已清理到仅保留错误边界用词条；请求/环境/历史界面为中文硬编码，待统一提取词条（阶段 0 已移除语言切换入口）。

6. **搜索**：阶段 1 为内存过滤（名称/URL/路径/方法），尚未索引请求体；`workspace_search` 已提供后端接口，可按需扩展。
