## 2. 关键选型说明

### 2.0 桌面 UI → gpui-kit / GPUI（阶段 1 后变更）

选择 **gpui-kit**（Zed 编辑器 GPUI 的组件库），理由：

- **纯 Rust 原生渲染**：Metal/WGPU/DX 直接绘制，无 WebView 体积与内存开销，跨平台一致。
- **单一语言栈**：UI 与领域层同 crate workspace（`crates/core` + `crates/app`），不再维护 TS/Rust 双类型与 IPC 序列化。
- **组件库完整**：Button/Input/Select/Editor/Switch/Tree/TitleBar/Notification 开箱可用，Lucide 全量图标集内建。
- **GPUI 数据流契合桌面工具**：Entity + subscribe 即响应式，无需前端路由/请求缓存库。

> 备选 Tauri + React：保留于 Git 历史；重写动机是消除 IPC 边界、统一构建链、获得原生渲染性能。

### 2.1 代码编辑器 → gpui-kit `Editor`/`EditorState`

请求 Body / 响应体编辑使用 gpui-kit 的 `Editor` 组件（内建多光标、语言高亮、Tab 策略），替代原先的 Monaco：

- `EditorState::new(window, cx).language("json").tab_size(TabSize { .. })` 直接获得 JSON 高亮。
- 纯 Rust 组件，与视图同进程，无跨端状态同步。

### 2.2 数据持久化 → 文件优先 + SQLite 索引（Git 友好）

参考 Bruno（纯文件存储）与 Yaak（SQLite + Git 同步层）的方案，采用**混合模式**：

- **持久化数据源为文件**：集合、请求、环境变量以 JSON 文件存储在用户选择的工作目录中。一个 Collection 就是一个文件夹，里面是请求文件。
- **SQLite 作为运行时索引/缓存**：应用启动时扫描文件目录建立索引，提供快速搜索与查询。代理流量、请求历史等临时/大量数据直接存 SQLite。
- **Git 为一等公民**：用户在 Collection 目录上 `git init` 即可获得版本控制与团队协作，无需额外同步层开发。

此方案的核心优势：
- 文件可直接 `git diff` / `git review`，协作透明。
- 零同步层开发成本，降低冲突处理复杂度。
- 用户可用任意 Git 工具（GitHub、GitLab、命令行……）管理。
- SQLite 仅存派生数据（索引、历史、代理流量），丢失后可重建。

文件结构示意：
```text
my-workspace/
├── thread.json                     # 工作区配置
├── environments/
│   ├── dev.json                    # 开发环境变量
│   └── prod.json                   # 生产环境变量
├── collection-a/
│   ├── collection.json             # 集合元信息
│   ├── get-users.json              # HTTP 请求
│   ├── create-user.json            # HTTP 请求
│   └── grpc/
│       └── hello-service.json      # gRPC 请求
└── collection-b/
    └── ...
```

> 详见 [03.database.md](03.database.md) 中文件格式与 SQLite 索引表的具体设计。

### 2.3 HTTP 客户端 → reqwest

- 支持 HTTP/1.1 与 HTTP/2。
- 支持流式响应（streaming body），适合大文件下载与 SSE。
- 可自定义 TLS 配置（忽略证书校验、指定客户端证书）。
- Cookie Jar 集成。

### 2.4 gRPC → tonic

- Rust 原生 gRPC 实现，基于 `hyper` 与 `prost`。
- 支持四种调用模式：Unary / Server-streaming / Client-streaming / Bidirectional-streaming。
- 支持 Server Reflection，无需 `.proto` 文件即可发现服务。
- 可动态加载 `.proto` 文件并编译为请求/响应结构。

### 2.5 代理引擎 → hyper + tokio + rustls（HTTP + SOCKS5）

- 基于 **hyper** 构建 HTTP/HTTPS 代理服务，处理 CONNECT 隧道与普通 HTTP 代理。
- 同时支持 **SOCKS5** 代理模式（参考 Yaak `yaak-proxy` 方案）。
- **rcgen** 动态生成域名证书，**rustls** 实现 MITM TLS 终结与重新加密。
- **tokio** 提供高性能异步运行时，支持数千并发连接。
- 代理在 tokio 运行时独立任务中运行，通过 `AppCore::take_proxy_events()` 轮询推送到 UI。

### 2.6 MQTT → rumqttc

- 支持 MQTT v3.1.1 与 v5。
- 异步架构（基于 tokio），可长时间保持连接并持续推送消息到前端。
- 支持 TCP / WebSocket / TLS 三种传输模式。

### 2.7 脚本运行时 → 预留（Phase 5），预选 QuickJS

- 首版不实现脚本引擎，前/后置脚本能力暂缓。
- 预选方案：**QuickJS**（Bruno 同款，`quickjs-emscripten`），轻量 JS 引擎、安全沙箱，用户可复用 Postman/Bruno 的脚本经验。
- 备选：**Rhai**（Rust 原生脚本引擎），但用户需学习新语法。
- 具体选型在 Phase 5 另立文档评估。

### 2.8 请求发送 → Rust 侧执行

所有网络请求在 Rust 侧发起（`AppCore::send_http` 等）。原因：
- gRPC（HTTP/2 + Protobuf）、MQTT（TCP 长连接）需要原生 TCP/TLS 控制。
- 代理抓包需要 MITM TLS 终结，只能在系统层完成。
- 取消/超时控制直接挂在 tokio 任务上，无 IPC 往返延迟。

> Bruno 能在 JS 侧发请求，是因为 Electron 主进程拥有完整 Node.js 运行时（`axios` / `@grpc/grpc-js`）且无 CORS 限制，与 Tauri WebView 机制根本不同。

## 4. 版本与兼容性约定

- Node ≥ 20，pnpm ≥ 9，Rust stable（≥ 1.85），Tauri CLI v2。
- 目标平台：macOS、Windows、Linux（详见 [06.dev-guide.md](06.dev-guide.md)）。
- 具体锁定版本以初始化工程时的 lockfile 为准，本文只约定大版本方向。
